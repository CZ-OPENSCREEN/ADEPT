Quick Start

Setting up Docker (first run only)

ADEPT runs inside a Docker container, so Docker is the only thing you need to install - all R packages, Python dependencies, and system libraries are bundled in the image.

  1. Install Docker: Docker Desktop on macOS or Windows, or Docker Engine on Linux - see docs.docker.com/get-docker. On macOS/Windows, launch Docker Desktop and wait until it reports that the engine is running.
  2. Check the install works: docker run --rm hello-world should print a short confirmation message.

Getting the ADEPT image (first run only)

There is nothing to build. Get the image in one of two ways; both give you an image named adept:latest, so every command in this documentation works unchanged.

Option A: from Docker Hub

docker pull bojke91/adept:latest
docker tag bojke91/adept:latest adept:latest

The second line gives the downloaded image the short name adept used throughout this documentation. (Alternatively, skip it and write bojke91/adept:latest instead of adept:latest in every command.)

Option B: from a file

If you received the image as a file (e.g. adept_1.0.0.tar.gz), load it with:

docker load -i adept_1.0.0.tar.gz

This restores the image as both adept:latest and adept:1.0.0; no extra tagging is needed.

Confirm the image is available with docker images adept. You should see adept listed with the tag latest.
latest always points to the newest release. To reproduce a specific analysis exactly (e.g. the results in the ADEPT publication), use the versioned image instead: bojke91/adept:1.0.0 from Docker Hub, or adept:1.0.0 after loading the file.

Running the pipeline

Place a metadata CSV and a quantification directory in a folder, write a config.yml (either by hand or via the configurator), and run:

# Open the configuration wizard
docker run -it --rm -v $(pwd):/data adept:latest --configure

# Run the pipeline
docker run --rm -v $(pwd):/data adept:latest
$(pwd) is macOS/Linux shell syntax for the current directory. In Windows PowerShell use ${PWD}, and in cmd.exe use %cd%.
The pipeline uses targets for dependency tracking. Re-running after a change recomputes only the outdated steps; unchanged upstream steps are reused from cache.

Pipeline Overview

The pipeline runs in five stages.

1
Read quantification files. Loads Alevin or STARsolo output into per-plate count matrices.
↓
2
DMSO QC. Scores control wells using robust z-scores and PCA, flags outliers and keeps the remaining DMSO wells as controls (by default all of them, with at least six per plate).
↓
3
Differential expression. Runs limma per compound × dose × timepoint. Two modes: per-plate (limma-voom) or collapsed across plates (limma-trend with duplicateCorrelation); see DE model.
↓
4
Visualisation. Volcano plots, DE heatmaps, UpSet plots, plate heatmaps, UMAP and PCA projections.
↓
5
Output. CSV tables, interactive HTML reports, and PNG/SVG figures, indexed by a single-page final report.

Config - DMSO Quality Control

Parameters for selecting high-quality DMSO control wells. Scoring combines gene-wise robust z-scores and PCA-based outlier detection; the algorithm is described in Best DMSO Selection.

FieldDescriptionDefault
z_threshRobust z-score threshold for outlier detection. A gene or PC score is considered outlying if |z| exceeds this value. Higher values are more permissive (flag fewer wells).3
top_nWhich DMSO wells to retain per plate as controls. "all" (default) keeps every well below the outlier threshold (median + 2 MAD); if that leaves a plate with fewer than min_keep wells, the best-ranked flagged wells are readmitted until it has min_keep. A number N instead keeps the N best-ranked wells per plate, even if one of them is above the outlier threshold (relevant only on plates with very few DMSO wells). In DMSO-versus-DMSO null tests, "all" was at least as well calibrated as 3 on both benchmark datasets. The published U2OS benchmark used 3."all"
min_keepOnly used with top_n: "all". Minimum number of DMSO controls per plate; below it, flagged wells are kept in rank order. On plates with few DMSO wells, losing a control costs more than including a mildly deviant one: in the GDPx4 per-plate null (8 DMSO wells per plate) the false-positive rate was 51%, 39% and 19.5% with 4, 5 and 6 controls. Plates with many DMSO wells never reach the floor.6
npcNumber of leading principal components (from a PCA of the DMSO wells) on which each well is tested as a robust-z outlier; every PC counts equally. Set to "auto" to use as many PCs as needed to explain 80% of variance (minimum 3).10
pca_weightWeight for the PCA component in the combined DMSO score. 0 = gene-level only, 1 = equal weighting (default), 2 = PCA-heavy. The pipeline logs the Spearman correlation between the two components to help calibrate this.1.0

Not exposed in the config: scale_pca (function argument, default FALSE) controls whether genes are scaled to unit variance before the PCA. The default lets highly expressed, highly variable genes dominate the leading PCs; TRUE gives every gene equal weight. The benchmark used the default.

Config - Well Quality Control

Optional per-well filter (qc.well) that drops failed or near-empty wells before DMSO selection and DE. Each well's total UMIs and number of genes detected are computed from the count matrix; a well is kept if it clears every active floor. Dropped wells are removed from the plate layout that DE uses, so they never enter a contrast, but they remain visible in the QC views (plate heatmaps, knee plots, sample UMAP/PCA) and in the DE compound heatmaps.

FieldDescriptionDefault
enabledTurn the filter on or off. A config with no qc.well block at all is treated as FALSE. The published U2OS benchmark ran with it enabled.FALSE (absent) / TRUE (configurator)
min_umisAbsolute floor on total UMIs per well.1000
min_genesAbsolute floor on genes detected (count > 0) per well.200
min_frac_medianRelative floor: drop wells below this fraction of the plate's median UMIs. 0 disables it. This is the intended lever for near-dead wells left by a cytotoxic compound that still sit above the absolute floor (e.g. 0.05).0
methodfixed applies only the floors above. inflection / knee additionally raise the cut to the DropletUtils::barcodeRanks threshold when it exceeds the floors. That threshold was designed for droplet data, where thousands of empty barcodes sit below the real cells; on a DRUG-seq plate every well contains cells, so on a clean plate it can land inside the real-well distribution and drop good wells. Inspect the knee plots first and opt in only for plates with a clear tail of failed wells.fixed
The full per-well table (UMIs, genes, thresholds, keep flag and reason) is written to knee_plots/well_qc.csv, and each plate's knee plot draws the applied cut and colours dropped wells red. A well removed here can leave a condition with a single replicate; such contrasts are then skipped by the per-group replication guard and listed in the *_skipped.csv logs.

Best DMSO Selection

DMSO control wells are scored using two independent signals which are then combined.

Part 1 - Gene-wise robust z-score outliers

For each gene, expression values across all DMSO wells are standardised using the median and median absolute deviation (MAD):

zg,w = (xg,w − median(xg,·)) / MAD(xg,·)

where xg,w is the normalised log₂ expression of gene g in well w. For each well, the number of genes with |z| > threshold (default 3) is counted. This captures gene-level expression instability.

Part 2 - PCA-aware outlier detection

PCA is computed on the DMSO expression matrix. For each of the top N PCs, well-level scores are standardised using the median and MAD across DMSO wells. The number of PCs with |z| > threshold is counted per well. This captures global transcriptomic deviations such as low library complexity, edge effects, or systematic artifacts.

Part 3 - Combined scoring

Gene-level and PC-level outlier counts are independently standardised (zero mean, unit variance) and combined as score = scale(gene_outliers) + pca_weight × scale(pc_outliers). With pca_weight = 1.0 (default), the two components have equal weight. The pipeline logs the Spearman correlation between them so the relative weight can be calibrated. Lower scores indicate more stable wells.

Within each batch, the DMSO dose group with the lowest median combined score is selected (with a per-dose summary written to dmso_dose_summary_batch_*.csv), and wells exceeding median + 2×MAD of the combined score are flagged as outliers. By default (top_n: "all") every remaining well is kept as a control, and a plate left with fewer than min_keep (6) wells has its best-ranked flagged wells readmitted. With a numeric top_n, the N best-ranked wells per plate are kept instead.

Config fields that control this step: dmso.z_thresh, dmso.top_n, dmso.min_keep, dmso.npc, dmso.pca_weight.

Returns a list with two elements.
$best_DMSO - data.frame of the wells kept as controls, per plate.
$bad_DMSO - data.frame of wells exceeding the outlier score threshold (median + 2×MAD).

Gene Filtering & Normalisation

filter_and_normalize_hybrid(counts, groups, use_filterByExpr = TRUE, min.count = 5, pct = 0.25)
Global pre-filter and TMM normalisation. Returns the logCPM matrix (used for modelling) and the DGEList object (used for per-contrast subsetting downstream). Both DE functions call it with min.count from analysis.de.min_count (default 5).

Filtering proceeds in two stages.

Stage 1 - Global presence-aware filter

Empty wells are dropped, counts are TMM-normalised, and edgeR::filterByExpr(group = condition, min.count = 5) selects genes that clear a CPM threshold in at least as many wells as the smallest condition. Because the test is per condition rather than on the mean across all wells, a gene expressed only at the top dose of one compound survives. Normalisation factors are recomputed after gene removal, and every contrast reads log-CPM from this one batch-level normalisation, so AveExpr is on a common scale across contrasts.

A legacy quantile filter (keep the top pct = 25% of genes by mean CPM, following the 2021 DRUG-seq paper) is retained behind use_filterByExpr = FALSE for A/B comparison only. It is biased against condition-specific genes, which is why it is no longer the default.

Stage 2 - Per-contrast filterByExpr

For each compound × dose × timepoint contrast, only the relevant treatment wells and matching DMSO wells are kept. edgeR::filterByExpr() is then applied to that subset with the same min.count, so a gene must be expressed in the groups being compared rather than in some unrelated treatment elsewhere on the plate. The number of genes that pass is recorded as n_genes_tested.

Dose-trend universe

The dose-trend test (see Collapsed dupCor DE) re-normalises the same wells with trend_min_count = 1 to build its own, more permissive gene universe. It relies on dose coherence rather than an expression cutoff to control noise, so it deliberately reaches below the floor the per-dose contrasts use.

A global filterByExpr would let a gene survive on the basis of high counts in group A, then be tested in a contrast between group B and DMSO where it has near-zero counts. The resulting test statistics are noisy and inflated. Per-contrast filtering avoids this.

Per-Contrast DE (run_single_contrast)

run_single_contrast(logCPM_global, dge_global, treat_wells, dmso_wells, treat_label, ctrl_label, well_to_group, min.count, min_resid_df = 2, min_group_n = 2, block, correlation)
Handles a single contrast: subset, filter, design, fit, eBayes, topTable.

For each compound × dose × timepoint, the function:

0
Replication guards: skips the contrast (writing a row to the *_skipped.csv log) if either group has fewer than min_group_n = 2 wells, or if the residual degrees of freedom (n_wells − 2) fall below min_resid_df = 2.
↓
1
Subsets the global logCPM and DGEList to the treatment and DMSO wells for this contrast.
↓
2
Runs filterByExpr() on the subset, giving each contrast its own gene universe.
↓
3
Builds a two-group design matrix (treatment vs. DMSO) with a contrast vector.
↓
4
Fits with lmFit: on log-CPM for limma-trend, or on voom() output for limma-voom (see DE model), adding block + correlation in dupCor mode.
↓
5
Calls eBayes(trend = (method == "trend"), robust = TRUE) for empirical-Bayes moderation (voom already carries the mean-variance trend in its weights).
↓
6
Returns the topTable with columns renamed to LFC, pval, padj.
Both models let the variance depend on expression level, which matters for RNA-seq-like data: limma-trend through eBayes(trend = TRUE), limma-voom through per-observation precision weights. robust = TRUE protects against occasional near-zero-variance genes that survive filtering. AveExpr is always reported on the log-CPM scale, so it is comparable between the two models.

Per-Plate DE (DE_limma_zQC)

DE_limma_zQC(Exp, CTRL, meta, best_DMSO_wells, out_dir, annotated_genes, ...)
Runs differential expression independently for each plate. No information is shared across plates.

The loop structure:

for batch in batches:
  for plate in batch:
    filter_and_normalize_hybrid(plate_counts)  → logCPM, dge
    for timepoint in plate:
      get DMSO wells at this timepoint
      for each compound × dose:
        run_single_contrast(treat_wells, dmso_wells, ...)

DMSO wells at a given timepoint are reused across all compounds at that timepoint. This mirrors the original pooled-DMSO design: every compound is compared against the same set of vehicle controls.

Use per-plate DE for QC (checking plate-to-plate consistency) or when only one plate per batch is available. For multi-plate experiments, the collapsed dupCor approach below is preferred. With method: auto the per-plate fits use limma-voom. Per-plate designs with two replicate wells and a handful of controls are hard to calibrate for any pipeline (DMSO-versus-DMSO null: ADEPT 20%, macpie 16% of contrasts with at least one false positive on GDPx4), so treat isolated calls from such screens with caution.

Collapsed dupCor DE (DE_limma_zQC_collapse_dupCor)

DE_limma_zQC_collapse_dupCor(Exp, CTRL, meta, best_DMSO_wells, out_dir, annotated_genes, ...)
Pools all wells with the same compound × dose × timepoint across plates within a batch. Uses limma::duplicateCorrelation() to account for within-plate technical correlation.

Why duplicateCorrelation

Wells on the same plate share library preparation and sequencing lane and are therefore not independent. duplicateCorrelation estimates the within-plate correlation ρ and lmFit uses it to adjust standard errors. The result is honest p-values that reflect the effective sample size.

With method: auto this path uses limma-trend on log-CPM. On voom-transformed data the consensus correlation was much larger (about 0.45 instead of 0.01 on the U2OS data) and the fit became anti-conservative (57% of DMSO-versus-DMSO null contrasts with a false positive, against 5% with limma-trend).

Effective sample size

neff ≈ ntotal / (1 + (nper_plate − 1) × ρ)

When ρ is appreciable, more plates matter more than more wells per plate.

Consensus correlation estimation

The correlation ρ is estimated once globally before the contrast loop, using the full expression matrix and full design. Per-contrast estimation would use too few wells for a stable estimate. The consensus ρ is then reused in every run_single_contrast call.

Single-plate batches

If a batch contains only one plate there is no cross-plate correlation to estimate; the batch is fitted within-plate with a plain lmFit and the consensus correlation is recorded as NA. Such batches still produce a _collapsed_dupCor.csv so downstream targets have a primary result.

Single-plate compounds

Compounds present on only one plate receive the dupCor correction but gain no cross-plate power benefit. These cases are flagged in the pipeline log; per-plate results may be more appropriate for them.

UMAP & Batch Correction

remove_umap_batch_effect(logCPM, meta, CTRL, batch_var, remove_batch)
Applies limma::removeBatchEffect() to the logCPM matrix before UMAP, removing plate-level technical variation while preserving treatment-level biological signal.

The batch correction uses a design matrix based on the treatment column to protect biological signal. The batch_var argument (default: plate_barcode) defines the technical grouping to be removed.

Within each batch, multiple plates undergo separate library preparation and sequencing, and plate-level effects are usually the dominant source of technical variance. Correcting only at the batch level leaves within-batch plate effects intact, which can dominate UMAP structure.

Downstream steps

After batch correction, the pipeline runs PCA, then Leiden clustering on the k-NN graph from the top PCs, then UMAP layout. Three interactive plots are produced:

UMAP by Leiden clusterCommunity-detection result. Clusters ideally correspond to compound × dose groups.
UMAP DMSO QCDMSO wells only, coloured by well-position category (centre / middle / edge) for spatial-bias inspection.

Limitations & Design Choices

Gene filtering trade-off

DRUG-seq has shallower sequencing depth than classical bulk RNA-seq, and most genes sit near the detection floor where count noise dominates. The presence-aware filterByExpr(min.count = 5) filter removes them before DE testing, reducing the multiple-testing burden and preserving power for the genes with real signal. The trade-off: a gene expressed at very low baseline that is only modestly induced can still be excluded. If a specific gene of interest is missing from a per-dose result, check n_genes_tested for that contrast and look for the gene in the DE_batch_*_dose_trend.csv table, whose more permissive universe (trend_min_count = 1) is designed to recover low-expression, dose-coherent responders.

Per-contrast FDR correction

The padj column uses Benjamini-Hochberg correction within each contrast (one compound × dose × timepoint). There is no experiment-wide correction across contrasts. This is standard for high-throughput compound screens, but borderline-significant genes should be interpreted with appropriate caution when the experiment contains many contrasts (e.g. 50+).

Per-contrast variance estimation

Each contrast estimates gene-wise variance from its own wells (the treatment replicates plus the control wells of the plate or batch). Avoiding pooled variance estimates protects against contamination from heterogeneous treatments, but yields fewer residual degrees of freedom. The eBayes(robust = TRUE) moderation compensates by shrinking estimates toward a global trend. The collapsed dupCor analysis pools wells within a batch and is preferred when more statistical power is needed.

BioMart network dependency

Gene annotation requires an Ensembl BioMart query on first run. If the primary mirror is unreachable, the pipeline retries across alternatives before failing. The annotation is cached after the first successful query, so subsequent runs do not require network access.

UMAP reproducibility

UMAP coordinates are reproducible within a single run (the seed is fixed) but are not comparable across runs with different samples. Adding or removing wells changes the k-nearest-neighbour graph, which changes the optimisation landscape, which changes the layout. Only relative distances within a single run are meaningful. For a stable reference layout across multiple runs, fit UMAP on a fixed reference dataset and project new samples onto it with umap::predict.

Upstream QC is out of scope

The pipeline starts from quantified count matrices. Read-level metrics such as alignment/mapping rate, ribosomal-RNA fraction and duplication rate are the responsibility of the upstream quantification tool. The pipeline does compute per-well library complexity itself (total UMIs and genes detected, shown in the plate heatmaps and knee plots) and can drop failed wells on that basis (see Well QC). DRUG-seq is a bulk, plate-based assay in which each well barcode is one sample, therefore it is quantified with single-cell tooling (Alevin/STARsolo). The barcode statistics should be read at the well level. There are no droplets, so droplet or cell-calling steps such as empty-droplet detection do not apply. Useful upstream sources:

  • alevinQC for Alevin and Alevin-Fry output (its barcode-rank/knee plots correspond to per-well complexity)
  • STARsolo's Summary.csv and Barcodes.stats files
  • FastQC + MultiQC for read-level diagnostics before quantification

Run an upstream QC tool first and inspect its output before treating the pipeline's results as final.
